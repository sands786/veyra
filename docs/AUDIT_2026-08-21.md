# Veyra Security Audit — 2026-08-21

## Scope

This was a fresh code-and-runtime security review of the Veyra full-stack application after the prior hardening release. The review covered the authentication and session boundary, protected tRPC procedures, workspace selection and ownership helpers, public claim and proof links, payment-route lifecycle and allocations, launchpad release decisions, private-market sealed bids, scheduled payroll execution, mainnet-only API contracts, database transactions, deployment code, the production dependency graph, and regression/build outputs.

## Verified findings and remediations

### 1. Launchpad release decisions could be overwritten

The release decision helper previously updated a request without checking its current state. That allowed a previously approved, rejected, or settled request to be re-decided and generated another audit event. The fix adds an explicit lifecycle state machine: `pending` can move to `approved` or `rejected`, and `approved` can move to `settled`; rejected and settled are terminal. The update and audit event now execute in one transaction with a current-state conditional.

### 2. Sealed-bid market aggregates were vulnerable to concurrent lost updates

The private-market bid path read the public volume and participant count, inserted a bid, and wrote aggregate values as separate non-transactional operations. Concurrent bids could therefore overwrite one another’s aggregate update. The fix serializes the market row with a transaction and row lock before validation, bid insertion, aggregate update, audit write, and return read.

### 3. Scheduled-payroll failures exposed raw internal errors

The scheduled endpoint returned `String(error)` and request URL details to its caller. That could disclose SQL, provider, or internal implementation details. The fix logs the full diagnostic server-side with a correlation ID and returns only a stable error code, correlation ID, and timestamp.

### 4. Public proofs could be created without receipt-backed evidence

The proof publisher checked route settlement but did not require a non-empty receipt or proof reference. The fix requires a trimmed `proofReference` before creating an active public proof link, preserving the product’s receipt-backed proof boundary.

### 5. Cookie-authenticated mutations lacked a browser CSRF boundary

Veyra’s production cookie is intentionally `SameSite=None` for the split Vercel/client and managed-backend deployment model. Before this pass, state-changing tRPC requests had no same-origin or Fetch Metadata check. The fix rejects cross-origin and `Sec-Fetch-Site: cross-site` POST requests before tRPC while retaining compatibility for internal requests without browser signals.

### 6. Payment-route persistence was not atomic

Payment-route creation could insert the route and then fail while writing route recipients or the audit event, leaving a financially incomplete draft. The fix wraps route, allocation, audit, and return-read operations in one transaction. Existing route validation and workspace ownership checks remain unchanged.

## Existing controls reverified

The review reverified recipient-scoped public claim disclosure, expiry-aware and race-safe claim redemption, exact unique route allocations, server-side payment-route transition enforcement, workspace-scoped queries, protected procedures, native Veyra account session handling, mainnet-only input schemas, public-link slug validation, and the absence of production dependency advisories.

## Validation

The final validation completed with TypeScript clean, **102 Vitest tests passing across 29 test files**, a successful production build, and `pnpm audit --prod --audit-level=high` reporting no known vulnerabilities. The client build continues to emit deferred route chunks; the initial client bundle remains approximately 823.73 kB after the previous performance pass.

## Residual boundaries

This audit does not claim that an external wallet has approved a real Starknet mainnet transaction, that a receipt has been confirmed on mainnet, or that the Vercel project owner has redeployed the latest GitHub revision. Those are operational evidence boundaries requiring the user’s wallet and the correct Vercel project access. The application now makes those boundaries explicit rather than fabricating settlement evidence.
